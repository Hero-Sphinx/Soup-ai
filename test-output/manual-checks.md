# Manual checks

Done by hand in a browser, against the app running locally. Screenshots are in this folder.

Setup: `npm run dev:local` and `npm run demo:local`.

1. **Disconnect.** I stopped the server while the `tiny-transformer` run page was open. The page changed to "Reconnecting…" and said "Showing data up to event #1520". Points 1520, Gaps detected 0, fingerprint hidden because the page no longer claims to be complete. Screenshot: [manual-1-reconnecting.png](manual-1-reconnecting.png). After I restarted the server the same page went back to "Live" with the same 1520 points, Gaps detected 0, and the fingerprint (5bbc97be) reappeared: [manual-3-live-after-restart.png](manual-3-live-after-restart.png). Limit of this check: the demo had already stopped, so no new points were written while the page was disconnected. It shows the page reconnecting and the server confirming it is complete. It does not show missed points being caught up; only the automated tests show that.
2. **A loss the automated tests do not catch, which I found by looking at that screenshot.** Both charts have a straight segment around steps 550–730. Each metric has 760 points but the last step is 934, so about 175 steps are missing. Cause: the demo client retries a batch for under a second and then drops it, and the server had been down for longer than that. The demo terminal printed `send failed, will continue` during the outage, which is that drop happening. The server and the page agree with each other (0 gaps) and both are missing the data. The page draws a straight line over the hole, so nothing tells the user. This is the "events the client never sent" case from section 1, seen for real.

3. **A run with no downtime has no hole.** A fresh `tiny-transformer` run (a new demo, different run id) shows "Live", 310 points = 155 per metric for steps 0–154, so no step is missing, Gaps detected 0, and the fingerprint is shown. Screenshot: [manual-2-live-fresh-run.png](manual-2-live-fresh-run.png). This supports the explanation in point 2: the hole comes from the client dropping data while the server was down, not from the page.

4. **A project's run list shows only its own runs.** Signed in with the first project's key, the list shows its three demo runs (1,520 points each) and a run named "Test" that I created through the page. The second project's runs (the fresh `tiny-transformer` from point 3, which had 310 points) are not in the list, although they are in the same database. Screenshot: [manual-4-run-list-first-project.png](manual-4-run-list-first-project.png). Limit: both demo projects are named "Demo", so the screenshot tells them apart only by point counts.

5. **One project cannot open another project's run by its URL.** Signed in with the first project's key, I opened the address of the second project's `tiny-transformer` run (the same run id that is "Live" with 310 points in point 3). The page shows "Not found" and "This run doesn't exist in your project", with 0 points. Screenshot: [manual-5-cross-project-not-found.png](manual-5-cross-project-not-found.png). Small bug I noticed in that screenshot: the page also said "No metrics yet. Points appear here as they arrive", which is misleading for a run you cannot see. That line is now hidden in this state (changed after the screenshot; not covered by an automated test).

6. **The other side of point 4.** Signed in with the second project's key, the list shows exactly its three demo runs (4,380 points each). The first project's runs and my "Test" run are not there. (No screenshot kept: the one I took also displays an API key.)
7. **Key rotation.** With the same project open in two tabs, I clicked "Rotate key" in one. The page showed the new key once. The other tab, still holding the old key, was signed out by itself with the message "That key is not valid (it may have been rotated)". Screenshot: [manual-6-old-key-rejected.png](manual-6-old-key-rejected.png). Bug I noticed in that screenshot: the header still showed "Demo", "Rotate key" and "Sign out" although the tab was signed out. Cause: a CSS `display: flex` rule was overriding the `hidden` attribute. Fixed in `public/style.css` after the screenshot. The demo client, which was still writing with the old key, started printing `send failed` at the same moment, so the old key was refused for writes as well as for reading.
